17:T14b7,## How I think about AI

I think AI is a tool for improving efficiency. It lets us focus more on implementing and testing our own ideas. But it also asks more of our taste, whether we are doing research or building products.

Research requires academic taste: producing work that is simple, effective, and elegant, like Kaiming He's. Here is a [Chinese-language post about Kaiming He and research taste](https://www.xiaohongshu.com/discovery/item/6a840aff0000000005028165?source=webshare&xhsshare=pc_web&xsec_token=ABbEXSdoif03AH48Ju-V4MZL9c0tfCosZlZ_meD72xxdg=&xsec_source=pc_share) if you are interested. Building products also takes good taste if we want to waste fewer resources and tokens and make something meaningful that people enjoy using.

I also think we still need a foundation in programming and mathematics. We should understand the principles we need for our work. AI can help with this too, by helping us learn the relevant knowledge quickly or apply it when we need it.

Before using AI, I think it is essential to break down the task and clarify its boundaries. During the work, we also need to think about where the human belongs in human-in-the-loop. Getting this right helps AI save us time and reduces the amount of repair work we have to do later.

## Tools and models I use

The tools I use regularly are Cursor, Codex, and WorkBuddy. The models I use include GPT-5.6 Sol, GPT-5.6 Terra, GPT-5.6 Luna, Claude-sonnet-5, Claude-opus-5, and Deepseek-v4.

I choose different models and working modes depending on the task. I mainly use models with strong reasoning capabilities, such as GPT-5.6 Sol, with Plan mode for discussing approaches, reviewing related work, designing prompts, and testing concepts. For engineering implementation, I mainly use models with strong coding capabilities, such as GPT-5.6 Sol, GPT-5.6 Terra, and GPT-5.6 Luna, with Target mode.

## Building RAGForge with AI

RAGForge is a modular RAG experimentation framework I have gradually built during my research. It started because I needed to try and compare different RAG approaches frequently. These usually involve data processing, text chunking, retrieval, reranking, generation, and evaluation. Implementing each approach separately meant a lot of repeated work and made it difficult to keep experiment configurations and evaluation methods consistent. So I abstracted the shared stages and, with Codex's help, built a framework whose components can be freely combined to quickly assemble and compare different RAG pipelines.

![RAGForge template page showing a pipeline graph and its configuration panel.](/assets/posts/working-with-ai/ragforge-templates.png)

*RAGForge's pipeline templates and editor.*

I was responsible for defining the framework's scope, the component-registration coding style, the core module abstractions, and the interfaces between modules. RAGForge uses a typed DAG to describe a pipeline, with retrievers, rerankers, generators, and evaluators designed as pluggable components. A compiler checks node references, input and output types, and topology. A runner handles dataset execution, caching, traces, and metric aggregation. The frontend uses React and ReactFlow for drag-and-drop pipeline composition, configuration editing, and viewing experiment results.

![RAGForge component library showing component descriptions and input and output types.](/assets/posts/working-with-ai/ragforge-components.png)

*The component library shows what each component does and its inputs and outputs.*

AI mainly acts as my development collaborator in this project. I first define a module's goal, inputs and outputs, and interactions with other modules. Then I ask Codex to understand the repository and carry out the implementation, changes across files, refactoring, testing, and debugging. I review and iterate based on the test results and the goals of the experiment.

For example, when checking early experiment code, Codex found overly permissive evaluation conditions for multiple-choice questions and baseline text truncation that could affect fair comparisons. I would then determine whether an issue was an implementation bug or a design problem and decide how to change it.

![RAGForge experiment run page with configuration, pre-run checks, and a task queue.](/assets/posts/working-with-ai/ragforge-run.png)

*The run page is where I check configurations, submit tasks, and view progress.*

RAGForge currently supports eight classes of experimental pipelines, including BM25, Dense, Hybrid, and Graph. It has been used in multiple RAG cases to compare approaches within the same framework. The user manual below covers data, components, pipeline design, experiment execution, and results management.

![RAGForge user manual with a table of contents and Chinese and English language options.](/assets/posts/working-with-ai/ragforge-manual.png)

*The RAGForge user manual.*

This project has helped me settle into a fairly consistent way of working with AI. I handle problem definition, architecture, module breakdown, interface design, and acceptance. AI speeds up implementation, refactoring, and testing, and broadens the scope of code inspection. I make the final technical decisions and check the experimental conclusions so that the code stays on track as it grows.18:T4b5,When a research direction changes, what remains is often not a particular model or dataset, but a way of judging the problem.

## The shared question

From access control to privacy-policy compliance, the work repeatedly involves three actions: understanding rules, locating evidence, and deciding whether that evidence supports a conclusion. RAG and fact-checking bring the same actions into large-language-model systems.

## From rules to evidence

Privacy regulations are not merely keywords to match. Applicability conditions, atomic obligations, and concrete disclosures in a document need to be distinguished. Reliable retrieval likewise asks for more than a semantically similar passage: the evidence must actually answer the question.

## What remains open

One current question is whether a system can distinguish “the document did not disclose it” from “retrieval failed to find the disclosure.” This distinction matters both to trustworthy compliance assessment and to deciding when a model should continue retrieving or stop.
