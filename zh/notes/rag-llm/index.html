从检索到证据链：RAG 与事实核查

从隐私文档中的分散证据出发，思考检索、验证与聚合如何协作，以及模型何时继续搜索、停止或暂缓判断。

RAGFact CheckingAdaptive RetrievalEvidence CoverageAgent

在隐私文本评估中，文本理解只是判断的起点。对于隐私合规、内容安全和事实核查等任务，系统不仅需要理解文本，还需要回答几个更关键的问题：相关证据在哪里，现有证据是否充分，这些证据能否支持当前结论，以及最终结论是否忠实于原始材料。

这也是 RAG 与事实核查在安全场景中的重要价值。相比直接让模型基于参数知识生成答案，更可靠的方式是将判断建立在可定位、可验证的外部证据之上，并进一步检查证据覆盖范围和支持关系。

因此，这类系统真正需要解决的，并不只是“如何检索更多内容”，而是如何围绕一个判断建立完整的证据链。

检索解决的是证据发现问题

在隐私合规、内容安全和事实核查任务中，相关信息往往分散在大量文档中。

例如，一项隐私披露可能同时出现在 Privacy Policy、Cookie Policy、Terms 和 Help Center 中；一则新闻的真实性判断可能需要结合正文、外部报道、事件背景以及图像信息。仅依赖单个段落或模型已有知识，很容易遗漏关键条件。

RAG 首先承担的作用，是从大规模文本或多模态信息中缩小搜索空间。

Sparse Retrieval 可以利用关键词和术语重合捕获明确线索；Dense Retrieval 通过语义表示发现表达不同但含义相关的内容；Reranker 则进一步重新评估候选与当前查询之间的相关性。

但这里需要区分两个概念：

检索相关性不等于证据有效性。

一段文本与问题高度相关，并不意味着它能够支持某个具体结论。例如，某段政策提到了某类数据，只能说明这一主题存在，并不能直接证明该数据被用于特定目的，也不能说明所有必要披露已经完成。

因此，Retriever 返回的本质上只是候选证据。

从“找到文本”到“验证证据”

证据驱动的安全分析需要在检索之后增加独立的验证过程。

对于一个候选片段，至少需要检查：

  • 文本是否真正讨论当前判断对象；
  • 主体、行为、数据类型和适用条件是否对应；
  • 原文表达的是支持、否定还是条件性关系；
  • 是否存在限定词、例外或否定表达；
  • 当前文本能够支持结论的哪一部分。

这实际上把问题从 semantic relevance 推进到了 evidence entailment。

事实核查研究中常见的支持、反驳和证据不足等关系，在安全分析中同样重要。尤其对于合规判断而言，一段“看起来相关”的文本如果并未蕴含所需事实，就不能被当作有效依据。

因此，一个更加合理的流程是：

Retrieval → Evidence Verification → Decision

而不是简单的：

Retrieval → Generation

前者将检索与判断解耦，使系统能够分别分析“有没有找到材料”和“这些材料是否足以支持结论”。

一个结论往往需要多条证据

很多安全判断无法由单个文本片段完成。

一项合规要求可能同时包含主体、数据类型、处理目的、接收方、用户权利和适用条件等多个信息要素；一个内容安全判断也可能需要同时验证人物、时间、地点、事件和来源。

这意味着证据验证往往是一个 multi-evidence reasoning 问题。

事实核查中的多跳检索和跨文档证据组合提供了重要参考：一个复杂结论可以被拆分为若干更小的待验证事实，再分别寻找证据并进行组合。

在合规评估中，也可以采用类似思路，将复杂要求拆分为更细粒度的 atomic obligations。每个原子义务对应明确的信息需求，再分别进行检索和验证。

例如，一项要求如果同时涉及信息类别、处理目的和接收方，那么三个信息要素可能分别出现在不同位置。只有当必要子项均得到有效支持，并且这些证据处于一致的适用条件下，才能进一步讨论整体要求是否得到满足。

因此，证据数量并不是关键，关键在于：

证据是否覆盖了结论所依赖的全部必要条件。

证据充分性是独立的问题

即使已经找到若干有效证据，系统仍需要判断这些证据是否“足够”。

这与传统检索任务存在明显差异。信息检索通常更关注是否返回相关结果，而安全评估还需要进一步判断：

是否还有影响最终判断的重要信息尚未找到。

Top-k 只能限定系统查看多少候选，无法证明搜索空间已经被充分覆盖。即使前几个结果都高度相关，也可能遗漏位于另一份文档、另一种表达方式或另一处上下文中的关键条件。

因此，证据充分性需要结合整个任务结构进行判断，包括：

  • 当前判断包含哪些必要信息要素；
  • 哪些要素已经获得有效证据；
  • 哪些要素仍然缺失；
  • 是否存在尚未检查的文档或信息来源；
  • 新一轮检索是否仍在产生新的有效证据。

这也是 RAG 从“检索增强生成”进一步走向覆盖感知的证据获取时需要解决的问题。

“没有找到”不等于“没有证据”

在安全和合规任务中，一个尤其重要的区分是：

NOT_FOUND ≠ NOT_DISCLOSED

NOT_FOUND 表示当前检索过程没有返回相关证据，是对检索系统状态的描述。

NOT_DISCLOSED 则是对被评估对象作出的结论，意味着在明确的文档范围和检查条件下，没有发现要求的信息。

前者不能直接推出后者。

检索失败可能来自查询构造不充分、Embedding 表示偏差、文档切分不合理、Top-k 过小，或者相关内容存在于另一份尚未检索的文档中。

因此，在输出“缺失”“未披露”或类似结论之前，需要先对 retrieval coverage 进行诊断。

更稳妥的系统应当能够区分：

没有证据、暂时没有找到证据，以及经过充分搜索后仍未发现证据。

这一区分对于隐私合规、内容审核和事实核查都非常重要，因为检索系统本身的失败不应被错误地解释为被评估对象存在问题。

Retriever、Verifier 与 Aggregator

从系统结构上看，这类任务可以拆分为三个相对独立的角色。

Retriever 负责尽可能发现潜在证据，并保留来源、位置和必要上下文。它回答的是“相关信息可能在哪里”。

Verifier 负责判断候选证据与具体事实或要求之间的关系，包括是否支持、是否矛盾、是否存在条件限制，以及证据是否足够明确。

Aggregator 负责将多个经过验证的局部结果重新组合起来，根据原始问题的逻辑关系判断整体证据是否充分。

这种拆分的意义在于能够定位错误来源。

如果最终判断不正确，可以进一步分析问题来自：

没有找到证据、错误接受了证据，还是错误聚合了证据。

相比直接观察一个最终标签，这种结构更适合需要可解释和可审计结果的安全任务。

全局语境与局部证据

证据也不能完全脱离上下文进行判断。

在长文档或跨文档任务中，一个局部片段的含义可能依赖章节标题、前文定义、适用主体或后续限定条件。如果只截取几个句子进行检索和验证，容易产生语义漂移。

因此，近年来的 RAG 工作开始更加关注全局语境如何指导局部检索。

一种思路是通过摘要、层次化索引或全局语义表示建立文档级背景，再基于当前信息需求定位局部证据。另一种思路是根据模型当前判断中的信息缺口动态发起查询，只补充真正影响结论的外部信息。

在内容安全和多模态事实核查中，这一点更加明显。模型不仅需要判断文本内部是否一致，还可能需要结合新闻报道、图像内容、事件背景和外部知识共同验证。

因此，好的检索系统并不是简单扩大上下文窗口，而是需要明确：

当前到底缺少什么信息，以及哪类证据最可能解决这个信息缺口。

从固定检索走向 Adaptive RAG

当检索成为推理过程的一部分后，一个自然的问题是：是否每个问题都需要相同数量、相同方式的检索？

答案通常是否定的。

一些问题可以直接由已有证据解决，而另一些问题可能需要继续搜索、改写查询或跨文档寻找补充信息。因此，Adaptive RAG 更关注四个连续决策：

When to retrieve What to retrieve Whether to continue When to stop

这些决策可以参考多种信号。

例如，仍未覆盖的事实或义务能够直接反映信息缺口；Verifier 的不确定性可以提示当前证据关系是否明确；不同证据之间出现 contradiction 时，可能需要进一步搜索；多轮检索如果持续返回相同内容，则可能说明搜索逐渐趋于饱和。

但单一信号通常并不足够可靠。

模型高置信度并不意味着结论正确，Retriever 的高分结果也不意味着证据有效，搜索结果重复也可能意味着查询本身存在偏差。

因此，更合理的停止条件往往需要综合考虑：

coverage、evidence quality、consistency 与 information gain。

结论也需要被验证

证据链的最后一个环节，是检查模型最终生成的结论是否忠实于证据。

这对应事实核查和 RAG 中常见的 faithfulness 问题。

即使 Retriever 找到了正确材料，Verifier 也识别出了正确关系，生成模型仍可能在组织答案时加入原文中不存在的信息，扩大证据能够支持的范围，或者忽略关键限定条件。

因此，可靠系统还需要检查：

Conclusion ↔ Evidence

之间的一致性。

对于安全分析而言，这一点尤其重要。很多错误并不是模型完全“编造”了一个事实，而是在已有证据基础上进行了过度推断。例如，原文只支持“可能”“部分”“特定情况下”，生成结果却变成了一个无条件结论。

因此，判断是否可靠，不仅要检查证据是否支持结论，还需要检查：

结论是否严格停留在证据允许的语义范围内。

RAG 与事实核查在安全中的作用

从隐私合规到内容安全，这些任务虽然具体目标不同，但共享一个非常相似的技术结构：

理解问题 → 明确信息需求 → 检索证据 → 验证证据 → 判断充分性 → 聚合证据 → 验证结论。

RAG 在这里承担的并不只是扩展模型知识，而是建立模型与外部事实之间的连接。

事实核查则进一步提供了判断这一连接是否可靠的方法：证据是否相关、是否支持、是否完整，以及最终结论是否忠实于证据。

因此，相比单纯追求更强的生成能力，更值得关注的是如何建立可追溯的证据链。

对于隐私合规，这决定了一项披露判断是否有充分依据；对于内容安全，这决定了一条风险判断能否被外部事实验证；对于 Agent 和工具调用场景，则进一步关系到模型依据哪些信息采取行动，以及什么时候应该停止、继续检索或 abstain。

从这个角度看，RAG 与事实核查并不仅是一组 NLP 技术，而是构建可靠 AI 安全分析系统的一种基础机制：让判断建立在可定位、可验证且足够充分的证据之上，同时确保最终结论不超出证据本身能够支持的范围。
