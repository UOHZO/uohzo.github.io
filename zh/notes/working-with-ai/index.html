我如何看待和使用 AI

我对 AI 的态度、平时怎么使用，以及和 Codex 一起搭建 RAGForge 的经历。

AIHuman-in-the-loop

我对 AI 的态度

AI 是提升效率的工具，能够帮助我们减少重复性工作，把更多精力放在想法的实现和验证上。然而，当“实现”本身变得容易，真正拉开差距的，是人自身的审美。做产品需要好的审美，才能做出有价值、受欢迎的产品；做科研同样需要学术品位，才能做出简洁、有效、优美的工作。

用好 AI 本身也是一种能力。我认为在使用 AI 之前应该先明确究竟要解决什么问题，问题的边界在哪里，任务可以如何被解耦和划分，以及什么模型和工具适用于这项任务等关键信息。在使用过程中，也要合理设计 human-in-the-loop，把人的判断放在问题定义、方案选择和结果验收等关键节点上。这样才能让 AI 的能力沿着正确的方向发挥，避免前面看起来进展很快，最后却花大量时间修正累积的错误。工具越强，越需要明确的目标和及时的纠偏。

我平时用哪些工具和模型

在论文实验方面，考虑到本地计算资源和实验成本，我通常会选择 Qwen3-7B、Qwen3-14B 等中小规模开源模型作为实验对象。这类模型部署和微调成本较低，方便进行 LoRA/SFT、RAG、Agent 或不同方法之间的可控对比，也更适合分析模型内部状态。

在科研探索和工程开发，我早期主要使用 Cursor，目前更多使用 Codex 和 Claude Code；此外，我也会使用 WorkBuddy 处理一些中文材料和办公类任务。我比较常用的模型有 GPT-5.6 Sol、Terra、Luna，Claude Sonnet 5、Opus 5，以及 DeepSeek-V4。

具体而言，我会关注各个模型厂商发布的技术报告，了解模型训练语料配比、训练方式；进而在完成具体任务时，根据任务类型、复杂度、可靠性要求、响应速度和成本进行模型选型。

GPT-5.6 Sol 是我处理复杂任务时最常用的模型之一。OpenAI 将其定位为面向复杂专业工作的旗舰模型，在 coding、research、science、cybersecurity 和 knowledge work 等任务上重点强化；同时支持更高的 reasoning effort。因此，我一般会把 Sol 用在问题定义、方案设计、复杂推理、研究梳理、Prompt 设计、代码架构以及较难的 debugging 上。GPT-5.6 Terra 更偏向能力与成本之间的平衡。因此，当方案已经比较明确，需要进行常规代码实现、模块修改、文档整理或者中等复杂度的分析时，我会倾向于使用 Terra。

Claude 系列里，对于更复杂、开放度更高的编程任务，我会使用 Claude Opus 5。Anthropic 的报告中特别强调了它在长链路 Agent、软件工程、专业知识工作和自我检查上的提升。这类特性使它比较适合大型代码库理解、复杂 debugging、长链路 Agent 任务、开放式分析，以及需要多轮检查和修改的任务。

DeepSeek-V4 则是在超需要兼顾效果、部署方式和成本的场景中的一个很有吸引力的选择。

我的工作流

在工作流上，我通常会按照 “明确问题—讨论方案—并行实现—结果验证” 的顺序推进。

  1. **先明确问题和验收标准。**我会提供任务背景、已有材料、约束条件和预期输出。例如，科研任务要说明待验证的假设、已有基线和实验条件；工程任务要说明接口、运行环境和完成标准。把这些信息交代清楚并存储为全局性的约束文档，可以减少模型自行补全错误前提，以及后续反复沟通的成本。
  2. **用 Plan 模式讨论方案。**对于复杂任务，我会先让推理能力较强的模型比较可行路径，指出关键假设、风险和最小验证步骤，我再判断方向是否值得推进。
  3. **按明确目标小步实现。**方案确定后，再进入以目标为导向的执行阶段，将任务拆成可以单独检查的模块，先完成最小可运行版本，再逐步扩展。复杂部分使用能力更强的模型，常规部分交给成本更低的模型；相互独立的任务可以开多个窗口并行处理。这样能缩短等待时间，也方便定位错误。
  4. **用证据验证结果。**代码通过实际运行、测试和日志检查；科研结论回到原论文、数据和实验结果；文字材料则核查事实、引用及论证是否一致。关键内容可以再交给另一个模型独立审查，通常我会选择不同公司的模型承担审查的任务。

Case：和 AI 一起做 RAGForge

RAGForge 是我在科研过程中逐步搭建的一套模块化 RAG 实验框架。最初是因为研究中需要频繁尝试和比较不同的 RAG 方案，通常涉及数据处理、文本切分、检索、重排、生成和评估等多个环节。如果每种方案都单独实现，不仅重复工作多，也很难保证实验配置和评测方式的一致性。因此，我把这些共性环节抽象出来，在 Codex 的协助下实现了一套组件可自由组合、能够快速搭建和比较不同 RAG pipeline 的实验框架。

RAGForge 的 pipeline 模板与编辑界面。

这个过程中，我负责确定框架的能力边界、组件注册型的代码风格、核心模块抽象以及模块间接口。RAGForge 使用 typed DAG 描述 pipeline，将检索器、重排器、生成器、评估器等设计为可插拔组件，通过 compiler 检查节点引用、输入输出类型和拓扑关系，通过 runner 统一负责数据集运行、缓存、trace 和指标聚合。前端则基于 React 和 ReactFlow，支持拖拽式组合 pipeline、修改配置和查看实验结果。

组件库里可以查看各个组件的用途和输入输出。

AI 在这个项目中主要作为我的开发协作者。我先确定模块的目标、输入输出以及与其他模块交互的方式，再让 Codex 理解整个仓库后，完成具体实现、跨文件修改、重构、测试和问题排查，之后由我结合测试结果和实验目标进行验收和迭代。

例如，Codex 在检查早期实验代码时，发现多选题评估条件过宽、baseline 的文本截断方式可能影响公平比较等问题。我会进一步判断它属于实现 bug 还是设计问题，再决定如何修改。

实验运行页面，可以在这里检查配置、提交任务和查看运行进度。

目前，RAGForge 已支持 BM25、Dense、Hybrid、Graph 等 8 类实验 pipeline，并已经用于多个 RAG case，在统一框架下比较不同方案。下面是框架的用户手册，整理了数据、组件、pipeline 设计、实验运行和结果管理的使用方式。

RAGForge 用户手册。

这个项目也让我形成了一套比较稳定的协作方式：我负责问题定义、架构设计、模块拆解、接口设计和结果验收，AI 负责加速实现、重构、测试和扩大代码检查范围。最终的技术决策和实验结论由我把关，避免代码越写越偏。
