17:T4ce8,> **核心问题：** 本文研究如何自动评估隐私政策中声明的数据实践是否违反数据最小化原则，并提出 DataMini，一个面向大规模隐私政策的 Human–LLM 协同评估框架。

## 概述

DataMini 将隐私政策中的数据实践表示为 **Action × Data × Purpose** 三元组，把抽象的数据最小化问题进一步拆成**固有违规（inherent violation）**与**情境违规（contextual violation）**两类；随后从大规模隐私政策中挖掘高频关联，经 LLM 与专家验证形成可复用的**合规映射（compliance mappings）**，先自动过滤明显合规的数据实践，再只对疑似违规项进行 Human–LLM 协同审核。

最终，DataMini 的数据实践抽取 **Accuracy 为 83.46%**；端到端违规识别达到 **Precision 0.9717、Recall 0.7063、F1 0.8180**；同时将专家需要阅读的信息量降低约 **80%**。

## 为什么做这个工作？

这项工作最初来自我参与的数据合规相关项目，并在“数据交易全流程监测关键技术”项目中进一步推进。这些项目关注的一个核心问题是：数据在收集、使用、共享、派生和存储等过程中，是否被合规地使用。无论是《个人信息保护法》还是《通用数据保护条例（GDPR）》，都对这此提出了数据最小化要求，即个人信息处理应当与处理目的直接相关，并限制在实现处理目的所必要的范围内。顺着这个问题，我进一步关注**服务提供者所声明的数据实践，是否真正与其服务目的相关且必要？**

隐私政策是一个很自然的评估对象，因为其是服务提供者向用户提供的、用于描述其数据收集、使用、共享等实践情况的**具有法律效力的文件**。隐私政策中会披露：

- 对数据执行了什么操作，即 **Action**；
- 处理了什么个人信息，即 **Data**；
- 为什么处理这些数据，即 **Purpose**。

因此，我将隐私政策中的一项数据实践形式化为：`Data Practice = (Action, Data, Purpose)`。例如：`(use, interests, advertising)`，即“为了广告目的使用用户的兴趣信息”。

> 需要明确的是：本文评估的是**隐私政策中声明的数据实践是否符合数据最小化原则**，并不验证企业实际运行时是否真的按照隐私政策执行。后者需要结合程序分析、流量、日志等运行时证据，是另一类关注实质合规的问题。


## 为什么需要自动化？

隐私政策通常篇幅长、技术术语多、结构复杂。普通用户很难且不愿意花大量时间去逐条判断其中的数据实践是否必要，但如果完全依赖隐私专家进行大规模审核，成本会非常高。因此，我的这篇工作的目标是建立一套：

> **细粒度、可扩展、可追溯，并且能够降低专家审核成本的自动化的数据最小化评估方法。**

## 现有方法有什么问题？

现有的数据最小化评估方法大致可以分为两类。

### 1 基于专家知识枚举必要数据实践

这类方法由专家预先定义“哪些数据实践是必要的”，然后将不在集合中的数据实践视为潜在违规。问题在于：

1. **数据最小化本身具有情境依赖性。** 同一种数据，在不同应用类型和不同目的下必要性可能完全不同。
2. 应用功能持续变化，很难依靠专家**穷举所有合理的数据实践**。
3. 这种方法难以扩展到大规模、快速变化的应用生态。

### 2 基于同类应用比较

第二类方法寻找与目标应用功能相似的应用，统计这些“同类应用”经常收集什么数据，并将高频出现的数据实践视为必要。这类方法隐含了较强的假设：

- 同类应用普遍收集的数据就是必要的；
- 收集的数据可以合理服务于其声明的目的；
- 总能找到数量和质量足够的可比应用。

这些假设并不总成立。此外，已有方法往往只关注 collect 这一数据收集行为，而数据最小化原则实际上还约束着 use、store、share 等更广泛的数据处理行为。

### 3 现有数据实践抽取方法粒度粗

PolicyLint、PurPliance、PoliGraph 等已有工具能够从隐私政策中抽取部分数据实践，但通常依赖规则、句法模式或较粗粒度的类别。例如，原文的 `collect email address` 可能被概况成 `collect personal information`。这样会错误地扩大文本所描述的语义范围。对于数据最小化评估而言，这种粒度损失会直接影响后续“这个数据是否必要”的判断。

### 4 直接使用 LLM-as-a-Judge 会带来伦理合规问题

一个最直接的方案是把整篇隐私政策交给 LLM，让模型端到端判断哪些数据实践不合规。然而：

- 过长的隐私政策会带来长上下文依赖和上下文遗忘问题；
- LLM 可能产生幻觉，判断缺乏明确的文本证据；
- 数据最小化本身具有主观性和情境依赖性，模型判断与专家判断仍然存在偏差；
- 最重要的是，在合规场景中，完全依赖自动模型做最终判断并不符合伦理道德规范。

因此，我的方法采用的是**自动筛选 + LLM 辅助 + 专家最终确认**的人机协同范式。

## 这项工作的挑战是什么？

### 挑战 1：“最小化”很难直接量化

法规要求数据处理应当与目的“相关且必要”，但不会为每一种 App、每一种功能直列出“允许收集哪些数据”的清单。因此首先要解决**数据实践违反了数据最小化原则**的定义问题。这不是一个普通的文本分类问题，而是需要把法律原则转化为可以计算的评估结构。在我们的方法之前，并未有相关工作提出合理的定义和量化方法，从我们收到的 OpenReview 审稿意见中的一条也可以看出。

![OpenReview 审稿意见](/assets/research/data-minimization/openreview.png)

### 挑战 2：“必要性”具有明显的情境依赖

同一数据实践在一个应用中可能合理，在另一个应用中可能不合理。例如：`(collect, financial records, functionality)`，对于金融类应用可能是必要的，但对于与金融无关的应用就可能存在问题。因此，不能只判断 Data 和 Purpose 的语义关系，还要考虑**应用类型等上下文**。

### 挑战 3：隐私政策是复杂、非结构化的长文本

后续评估依赖准确的数据实践三元组。如果最前面的 Action、Data、Purpose 抽取错了，后面的合规判断再准确也没有意义。然而，在抽取数据实践时我发现存在如下问题：

- 同义表达很多；
- 一个段落中可能出现多个 Action、Data、Purpose；
- 三者之间的对应关系并不总在同一句话中；
- 直接输入 LLM 进行抽取又容易受到长上下文和幻觉影响。

因此需要解决**细粒度抽取 + 标准化 + 关系验证**的问题。

### 挑战 4：不能把“高频”直接等同于“合规”

我们希望从大规模隐私政策中学习常见模式，以减少专家逐条枚举知识的成本，但现实中的高频行为本身也可能违反数据最小化原则。所以统计规律只能用于产生**候选知识**，不能直接作为合规标准。这也是为什么 DataMini 后面还需要 LLM 与专家共同验证 candidate mappings。

### 挑战 5：准确性与人工成本之间存在矛盾

完全人工最可靠，但无法扩展；完全自动效率高，但在具有法律和伦理判断属性的任务上可靠性不足。因此我们认为真正的问题是：

> **哪些部分可以安全地自动化，哪些部分仍然应该交给人？**


## 核心创新点与贡献

### 1 对数据最小化违规进行细粒度建模

我们以 **data–purpose relevance** 为基础，把原本抽象的数据最小化违规分成两个层次：

1. **固有违规（Inherent Violation）**，即这个 **Action × Data** 对当前 **Purpose** 本身是否合理？这类问题不需要知道应用具体是什么类型，仅从数据、行为和目的之间的关系就可以发现异常。例如，如果某个目的与所处理的数据之间明显缺乏必要关联，就可能构成固有违规。因此，这类问题主要检查 `Purpose → Action × Data`。
2. **情境违规（Contextual Violation）**，即这个 **Data / Purpose** 放在当前 **App Type** 下是否合理？有些数据实践本身并没有明显问题，但放在某个应用场景中就可能不合理。因此需要额外检查 `App Type → Purpose` 以及 `App Type → Data`

这一点解决的是**问题如何被定义和计算**。

### 2 提出 Extract–Combine–Verify 数据实践抽取 Pipeline

通过：`基于 LoRA 微调后的模型抽取 → Ontology 标准化与组合 → 基于检索的两轮验证`，将复杂隐私政策转换为细粒度的 `(Action, Data, Purpose)` 三元组。

相比直接分类或规则抽取，这个设计同时解决了：细粒度语义抽取；同义表达标准化；元素组合爆炸；三元组是否真正被原文支持的问题。

### 3 从大规模真实隐私政策中构建可复用的合规基线

我们从 **12,519 份隐私政策**中抽取 **875,499 个数据实践三元组**，利用 PMI 和共现概率挖掘高频候选模式，再由 LLM 和专家验证，最终得到 **5,130 条 compliance mappings**。将专家知识被转化为一种**可复用、可扩展的合规基线**。

### 4 Human–LLM 协同，而不是简单 LLM-as-a-Judge

合规映射首先过滤明显合规的数据实践，只将未完全匹配的实践视为 suspected violations，再由 LLM 分析，最终由专家确认。

这把专家工作从：`阅读整篇政策 → 自己发现问题 → 分析问题`，变成：`查看系统筛出的疑似问题 + 简短理由 → 验证`。实验中专家需要处理的信息量降低约 **80%**。

## 方法
### 1 总体框架
DataMini 整体分为两部分：

![DataMini 合规基线构建与人机协同评估框架](/assets/research/data-minimization/overview.png)

1. **合规基线构造（Compliance Baseline Construction）**，第一部分的目标是从大规模隐私政策中构建一套可复用的“合规基线”。
2. **人机协作评估（Human–LLM Collaborative Evaluation）**，第二部分则使用这套基线评估新的隐私政策：明显合规的数据实践自动过滤，只把疑似违规项交给 LLM 和专家进一步审核。

这也是整个工作的核心思路：

> **机器处理大量重复且相对明确的判断，把专家精力留给真正困难的边界案例。**

### 2 具体方法
### 2.1 数据实践表示

我们将隐私政策中的一项数据实践表示为 `(Action, Data, Purpose)`。为了统一不同隐私政策中的表达，我们分别构建了 Action、Data 和 Purpose 三类 ontology。Action ontology 包含 51 类行为，Purpose ontology 包含 56 类处理目的；Data ontology 则在已有 OPI 基础上补充了 266 个数据术语。应用上下文采用 Google Play 的 48 个应用类别。

在此基础上，我们把数据最小化违规分成两类：

- **固有违规（Inherent violation）**：不依赖具体应用类型，仅从 Action、Data 和 Purpose 之间的关系就可以发现问题；
- **情境违规（Contextual violation）**：需要结合具体应用类别判断，同一数据实践在一种应用中可能合理，在另一种应用中可能不合理。

这两类违规对应三类关系，即 `Purpose → Action × Data'、`App Type → Purpose'、`App Type → Data'。


### 2.2 合规基线构造

DataMini 首先从大规模隐私政策中构建一套可复用的 compliance mappings。

#### 2.2.1 数据集构造

我们从 36,167 个 Google Play 应用包名出发，获取应用类别、标题、隐私政策链接等 metadata，并抓取对应隐私政策。过滤掉无效包名、不可访问链接和非英文隐私政策后，最终得到 12,519 份隐私政策以及对应的应用 metadata。这样做的目的是获得一个规模足够大、覆盖多个应用类别的数据集，用于后续统计哪些数据实践经常一起出现。

#### 2.2.2 数据实践抽取

我们设计了一个三阶段流水线以准确抽取数据实践：**Extract → Combine → Verify**

![数据实践抽取 Pipeline](/assets/research/data-minimization/pipeline.png)

（1）提取：首先将隐私政策网页清洗为保留文档结构的 Markdown。随后以段落为单位，使用 LoRA 微调后的 LLM 分别抽取 Action、Data 和 Purpose。采用段落级抽取而没有直接要求模型一步生成完整三元组，是为了让模型在保留局部上下文的同时避免直接处理整篇长文档，此外一个段落中经常同时出现多个元素，直接生成关系更容易遗漏或错误匹配。

（2）组合：抽取后的词语存在大量同义表达，例如 `surname` 和 `last name` 实际上表示同一种数据。因此，我们构建了 Action、Data 和 Purpose 三类 ontology，使用 embedding similarity 将 将抽取到的 raw element 映射为统一术语。随后组合 `Action × Data` 的候选 pair，而不是直接把 Action、Data、Purpose 做完整笛卡尔积。

（3）验证：这一阶段用于判断候选关系是否真的被原文支持。我们没有直接让模型处理整篇隐私政策，而是从原文中检索证据。Retriever 使用 BGE-M3，并采用 structure-aware chunking，优先按标题、章节和段落结构切分文档。验证分成两轮，第一轮判断“这个 Action–Data pair 是否真的存在？”。如果存在，再进入第二轮判断“这个 Action–Data pair 对应哪些 Purpose？”，最终形成完整的数据实践三元组。这里使用检索增强生成的目的不是引入外部知识，而是让每一个判断都基于隐私政策原文中的证据。同时，两轮验证还可以避免 Action、Data、Purpose 直接做笛卡尔积带来的组合爆炸。

#### 2.2.3 挖掘高频映射

在 12,519 份隐私政策上运行数据实践抽取后，我们一共得到 875,499 个 data practice triples。随后从中挖掘三类候选映射：Purpose → Action × Data、App Type → Purpose 和 App Type → Data。这些映射用来描述：某种 Purpose 下常见的 Action–Data 组合；某类应用常见的 Purpose；某类应用常见处理的数据类型。

首先使用 PMI 过滤 Data 和 Purpose 之间关联较弱的组合，然后再使用共现概率进一步过滤低频偶然关系。需要强调的是**高频只用于生成 candidate mappings，并不代表这些关系一定合规。**因为现实中某些不合理的数据实践也可能大量出现。

#### 2.2.4 合规映射验证

因此，candidate mappings 还要经过 LLM 和专家验证。
我们使用 3 个不同的 LLM 分别判断某条 mapping 是否符合数据最小化原则，每个模型输出 Y/N 和 rationale，再通过 majority voting 得到 preliminary consensus 和 confidence。最后由领域专家综合模型判断和理由，给出最终结论。经过这一过程，形成可复用的合规映射。

---

### 2.3 人机协作评估

对于一个新的目标应用，评估流程分成三步。

（1）预处理：获取目标应用的 privacy policy、category、description 等 metadata，然后利用 Extract–Combine–Verify 流水线抽取数据实践。

（2）合规映射匹配：每条数据实践都会与三类 compliance mappings 匹配。如果 `Purpose → Action × Data` 不匹配，则认为存在 **潜在的固有违规**。如果 `App Type → Purpose` 或 `App Type → Data` 不匹配，则认为存在 **潜在的情境违规**。这里“不匹配”并不意味着直接判违规，只表示这条实践值得进一步审核。

（3）审核
疑似违规项会连同应用 metadata 和隐私政策一起交给 LLM。LLM 需要判断是否真的违规、属于固有违规还是情境违规，并给出理由。最后由领域专家进行最终确认。

## 实验

实验主要验证三个问题：

- 数据实践是否能够被准确抽取？
- 构建出的 compliance baseline 是否可靠？
- DataMini 最终能否有效识别数据最小化违规？

### （1）数据实践抽取效果

Baselines：实验比较了 6 个开源 LLM，即 Qwen2.5-7B、Qwen2.5-14B、Gemma-3-12B、Baichuan2-7B、Llama-3.1-8B
、Baichuan2-13B。同时比较微调前后的表现，以及当前效果最好的数据实践抽取基线 PurPliance、PolicyLint 和 PoliGraph。

Metrics：元素抽取使用 Exact Match F1 和 ROUGE-L F1。完整 data practice triple 另外采用 embedding-based semantic similarity。基于 Action、Data 和 Purpose 三部分相似度的平均值，设计：

- **Coverage**：参考三元组被预测结果覆盖的程度；
- **Accuracy**：预测三元组与参考三元组的一致程度。

Implementation：LoRA 参数为 rank = 8；scaling factor = 16；dropout = 0.05。训练使用单张 NVIDIA A100-SXM4 40GB。

Results：微调之后，所有模型的抽取效果都有明显提升。相比 base models 的 ROUGE-L F1 提升约 `0.17–0.57`，Exact Match F1 提升约 `0.17–0.58`。同时，微调后的 LLM 整体明显优于 PurPliance、PolicyLint 和 PoliGraph。其中 **fine-tuned Gemma-3-12B** 综合表现最好，因此被选作后续数据实践抽取模型。最终在全部 12,519 份隐私政策中抽取出 875,499 个 data practice triples

![LLM和现有工具的数据实践抽取表现](/assets/research/data-minimization/lora.png)

这个实验的意义是：先验证后续合规判断所依赖的结构化输入是可信的。如果数据实践本身抽取不准，后面的违规识别结果也没有意义。

### （2）合规基线的可靠性

主要观察两个指标：

- **Violation Rate**：候选 mappings 中不符合数据最小化原则的比例；
- **Candidate Set Size**：当前阈值下保留的候选数量。

阈值太低会保留过多噪声，增加人工审核成本；阈值太高又可能丢失大量有效模式。因此，本质上是在 candidate quality、coverage 和 manual verification cost 三者之间做 tadeoff。

### （3）PMI 与共现概率阈值

实验中有一个很重要的发现：**高共现关系仍然可能违规。**例如，“personal information → service improvement” 这种宽泛表述在大量政策中都很常见，因此统计上关联很强，但从数据最小化角度仍可能是不合理的。这说明不能把“高频”直接当成“合规”，必须保留后续的 LLM 和专家验证。

### （4）违规识别

把合规映射产生的 preliminary violation labels 与 expert ground truth 比较后，Accuracy = 82.76%。说明 compliance baseline 本身已经能够较可靠地进行前期筛选和违规类型判断。

此外，整个违规识别的 Precision = 0.9717、Recall = 0.7063；F1 = 0.8180。其中，高 precision 说明 DataMini 的违规判断相对谨慎。Recall 为 0.7063，说明仍有部分真实违规没有识别出来，这主要和数据最小化本身的复杂性和主观性有关。某些案例需要同时结合具体应用场景、功能语义、数据敏感性和法律要求，当前模型仍可能与专家判断存在偏差。这也是为什么本文最终采用 Human-in-the-loop，而没有把整个流程设计成完全的自动化系统的原因。
